* Clusters

| Cluster | Nodes                                                                                     | CNI     | NixOS add-ons                     | From ~main~'s Argo CD             |
|---------+-------------------------------------------------------------------------------------------+---------+-----------------------------------+-----------------------------------|
| ~main~  | ~k8s-node-1~ … ~k8s-node-3~, all servers                                                  | Cilium  | kube-vip, OpenBao, Argo CD        | the whole platform, Reloader      |
| ~edge~  | ~k8s-node-x86-64-1~ (server, SQLite), ~k8s-node-aarch64-1~, ~k8s-node-aarch64-2~ (agents) | flannel | ~argocd-spoke~, mktxp credentials | Reloader, monitoring agent, mktxp |

Every node also gets the Gateway API and volume snapshot CRDs and democratic-csi (~zfs-generic-iscsi~ against storage-station, storage class ~iscsi~, snapshot class ~iscsi-snapshot~). Each cluster keeps its volumes in its own dataset (~tank/kubernetes~, ~tank/kubernetes-edge~). Both run dual-stack.

* Defining a cluster

Clusters and their nodes are declared in ~kubernetes.clusters~ in ~flake.nix~; ~default.nix~ defines those options, the ~kubernetes-node~ module and the generated ~nixosConfigurations.<node>~ and ~deploy.nodes.<node>~; ~addons.nix~ holds the add-ons a cluster lists in ~modules~. Add-ons read per-cluster values from ~config.kubernetes.cluster~. Every node joins the cluster's ~init~ server at ~<init>.local~.

A cluster managed by ~main~'s Argo CD (a spoke) needs:
+ its own CA, generated once and agenix-encrypted (~ca~ in its definition); k3s only takes it before its first start
+ the ~argocd-spoke~ add-on, which installs that CA as k3s's server and client CA and gives the ~argocd~ client certificate cluster-admin
+ a DNS name for its API server that Argo CD's pods resolve (~edge.burned.host~)
+ on ~main~, its Argo CD cluster Secret (~secrets/argocd-cluster-<name>.age~, shipped by the ~argocd~ add-on) and a destination in the ~platform~ project (~infra/argocd-bootstrap.yaml~)

* Network and names

The nodes live on VLAN 33, which carries only the clusters; addresses are DHCP reservations and EUI-64 SLAAC. IPv6 is ULA-only (~fd71:895d:e328:33::/64~), masqueraded to the GUA by the router; NAT64 (~64:ff9b::/96~) serves IPv4-only destinations.

* Workload

| Layer          | Tool                                  | Where                                 | Command                   |
|----------------+---------------------------------------+---------------------------------------+---------------------------|
| Infrastructure | NixOS (deploy-rs, nixos-anywhere)     | ~default.nix~, ~addons.nix~, ~infra/~ | ~deploy .#k8s-node-1~     |
| Platform       | Argo CD on ~main~, project ~platform~ | ~platform/~                           | ~nix run .#push-platform~ |

NixOS holds what has to exist before Argo CD runs: k3s, the CNI, kube-vip, democratic-csi, OpenBao, Argo CD and the secrets they need. ~push-platform~ pushes ~platform/~ from the working tree to ghcr.io as ~platform:latest~, annotated with the commit and whether the tree was dirty; Argo CD picks it up within minutes. The cluster runs whatever was pushed last, so push before reinstalling.

The root Application (~infra/argocd-bootstrap.yaml~) syncs the top-level files: ~platform/addons.yaml~ (one ApplicationSet per add-on that runs on several clusters) and ~platform/groups.yaml~ (one Application per group of ~main~'s platform). Groups sync side by side and retry until what they need from another group exists; sync waves order the inside of a group.

| Group            | What (sync waves)                                                                                                                                                                                                     |
|------------------+-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| ~foundation/~    | cert-manager (0); Istio ambient (1-3); vault-config-operator, External Secrets (10); OpenBao contents, ~ClusterSecretStore~ (20); certificates, issuers, ~burned-gateway~ (29-32); Keycloak login for OpenBao (59-60) |
| ~data/~          | CloudNativePG operator (0); Barman Cloud plugin (10); RustFS and its ~rustfs-users~ Job (33-35); ~default-postgres-cluster~ and its backups to RustFS (39-40)                                                         |
| ~identity/~      | Keycloak operator (0); database, Keycloak at ~auth.burned.host~, ~burned~ realm (50-52); clients added by the ~keycloak-config~ Job (53-54)                                                                           |
| ~observability/~ | alerting rules, Loki, Tempo, Pyroscope, Grafana, Alloy, OpenTelemetry Operator, VictoriaMetrics (69-72); ~Instrumentation~ (80); Kiali (95-96)                                                                        |
| ~apps/~          | Nextcloud at ~nextcloud.burned.host~ (94); Cloudflare tunnel (95)                                                                                                                                                     |

An app gets its namespace, a database in the shared cluster (a ~Database~ and ~DatabaseRole~ in ~postgres~, as in ~platform/identity/keycloak.yaml~), a RustFS bucket and user (a ~RandomSecret~ in ~platform/foundation/openbao.yaml~, a line in the ~rustfs-users~ Job and its secret in ~platform/data/rustfs.yaml~, an ~ExternalSecret~ in its namespace).

* Reinstalling

+ Volumes have deterministic names and ~Retain~ policies, so a reinstalled cluster re-adopts every dataset. To start an app from scratch, delete its datasets on storage-station while the cluster is down.
+ Postgres is the exception: CloudNativePG's ~initdb~ wipes an existing data directory, so ~default-postgres-cluster~ bootstraps with ~recovery~ from the newest base backup in RustFS plus the archived WAL. Take a backup before a planned reinstall:
#+begin_src bash
kubectl cnpg backup default-postgres-cluster -n postgres --method plugin --plugin-name barman-cloud.cloudnative-pg.io
#+end_src
  A new environment with an empty bucket needs ~initdb~ once.
+ One server at a time: drain it, ~kubectl delete node <node>~, install it with its host keys and machine ID (see the main README); it joins as a new etcd member. Reinstalling the ~init~ server needs another server as ~init~ first, or it starts a new cluster.
+ Adding a CA to an existing cluster means resetting its k3s state: stop k3s on all nodes (~k3s-killall.sh~), delete ~/var/lib/rancher~ (only ~agent/~ on agents), deploy, start k3s.
